# M7: Playtest Fixes and Usability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the bugs found in the first full playtest (stuck units, no way to help build) and add the usability layer the player asked for: contextual cursors, trackpad gestures, a Controls settings tab, building delete with a partial refund, a tech tree view, a switchable right-side panel (scores and villager activity), camera buttons (home and zoom), a local match log with a statistics screen, and more dynamic music.

**Architecture:** Gameplay fixes go first, in the ECS and pathfinding layers, guarded by headless simulations. Then input and settings (one place for all bindings), then HUD pieces in the DOM glass UI, then the new `src/stats/` module (a score tracker that lives with the match, enters the save as `schemaVersion` 2, and feeds a localforage match log), and finally music. GameScene is at 393 lines: all new wiring goes into `src/scenes/game/` helpers.

**Tech Stack:** Phaser 3.80, TypeScript strict, Vite, Vitest, Miniplex 2, Zustand vanilla, localforage, zod. No new dependencies.

**Spec:** `CLAUDE.md` §9 M7 (binding), together with §4, §5.4, §6, §7, §10, §11.1, §12. The player's own words (Hungarian) are quoted in the ledger's header.

## Design Decisions (controller rulings — binding)

1. **Stuck units — three layers of defence.**
   - (a) `createBuilding` callers that place a foundation (human `BuildPlacement`, `WallLinePlacement`, the AI's placement) evict the units on the footprint: each one gets its `movable.path` replaced by a path to the nearest passable tile outside the footprint (and its orders are kept, so a builder still builds). This lives in one shared helper, `src/ecs/evict.ts`, `evictUnitsFrom(world, map, origin, footprint)`.
   - (b) `MovementSystem` gets the `MapData` (optional constructor argument, as the throttled systems already take one): before advancing onto `path[0]`, if that tile is no longer passable and is not the path's last tile, the unit stops and re-plans with `moveIntent` = the path's last tile.
   - (c) `findPath` / `findPathToNearest` from an impassable start tile first find the nearest passable tile (BFS that may cross impassable tiles, bounded by the map) and return the escape steps followed by the normal path. A unit standing on blocked ground can always leave.
   - The "two villagers side by side" report must be reproduced headlessly first (systematic debugging). If it is a separate cause, it is fixed at its root and gets its own regression test.
   - Guard: `src/ai/strategies/stuckUnits.sim.test.ts` runs a seeded 4-AI match on 96×96 (Hard, ~15 game minutes) and asserts that no living unit stands on an impassable tile for longer than 2 s and that no unit with an order stays on the same tile, without moving, for longer than 20 s. If a full sim is too slow for the suite, it runs with the existing sim pattern (the `*.sim.test.ts` files) and its budget.
2. **Help build.** In `OrderIssuer`, a right-click on an own building that is `underConstruction` (and not dying) gives every selected own villager (`gatherer`) a `buildCommand` with that `targetId`; other selected units get a move. The order sound is `unit_move`. This also applies to the command gesture (Decision 4).
3. **Contextual cursor.** A pure function `cursorFor(ctx): CursorKind` in `src/ui/cursor.ts`. `CursorKind = 'default' | 'move' | 'gatherWood' | 'gatherGold' | 'gatherFood' | 'build' | 'attack' | 'forbidden'`. It is decided from the selection (own units only; buildings never change the cursor) and the hovered tile, with exactly `OrderIssuer`'s targeting rules (`OrderIssuer` exposes its target resolution as a pure function, so both share one rule): an enemy target → `attack` if any selected unit attacks; an own unfinished building → `build` if a villager is selected; a resource node → the gather kind for villagers; an impassable tile without a target → `forbidden`; otherwise `move`. During placement mode the cursor is `default` (the ghost is the feedback). Cursors are 32×32 SVGs built in code (`src/ui/cursors.ts`, data URIs, hotspot per kind), drawn in the UI's style (amber `#f5a857` outline over a dark fill); they are set on the canvas element only when the kind changes.
4. **Controls settings.** `Settings` gains `controls: { commandGesture: 'ctrl' | 'meta' | 'alt' | 'none'; scrollMode: 'auto' | 'zoom' | 'pan' }` (defaults `'ctrl'`, `'auto'`). The settings JSON key stays `isorts.settings.v1`: the zod schema fills missing fields from the defaults, so old blobs load. The right button always issues a command; a left click with the gesture's modifier also does (and does not select). `KeyAction` grows: `home` (`KeyH`), `scorePanel` (`Tab`), `villagerPanel` (`KeyV`), `techTree` (`KeyT`), `deleteBuilding` (`Delete`). `RESERVED_KEY_CODES` stays as is, and none of these defaults clash with the pan keys. The settings screen gets two tabs, "Hang" (the M6 content) and "Irányítás" (gesture, scroll mode, then every key binding in a list grouped as "Kamera" and "Parancsok"). The defaults button resets both tabs.
5. **Scroll and trackpad.** One pure classifier `wheelIntent(e, mode): 'zoom' | 'pan'` in `src/scenes/systems/wheelIntent.ts`. A `ctrlKey` wheel is a pinch, so it is always `'zoom'`. Mode `'zoom'` or `'pan'` forces that intent. Mode `'auto'` reads a trackpad from `deltaMode === 0` together with (`deltaX !== 0` or a non-integer `deltaY` or `|deltaY| < 40`), and returns `'pan'` for it and `'zoom'` otherwise. A pan moves the camera by `(deltaX, deltaY) / zoom` world pixels. A pinch zooms by `exp(-deltaY * 0.01)` around the pointer. `preventDefault` on the canvas wheel stops the browser page zoom on pinch.
6. **Delete building.** A pure `refundFor(cost, p)` in `src/game/refund.ts`:
   - For `p ≤ 0.5`: `pct = Math.round((1 - p) * 80)`, and each resource is `Math.round(cost[r] * pct / 100)`.
   - For `p > 0.5`, and for finished buildings: zero.
   - `p = elapsed / totalTime`, clamped to [0, 1].
   - Tests: `p = 0` gives 80 %; `p = 0.49` gives 41 %; `p = 0.5` gives 40 %; `p = 0.51` gives 0.

   Deleting goes through `killEntity`, so the existing death path (fx, population cap, builder release, victory check) applies. A deleted finished building does not count as a kill for anyone's score.

   UI:
   - A small "Törlés" button with a trash icon on the selection panel, for own buildings only.
   - On a site, the button shows the refund (e.g. "Törlés · +41 %").
   - The first press arms a 3 s inline confirmation and the second press executes. The `deleteBuilding` key does the same.
   - The AI never deletes.
7. **Tech tree.** `src/ui/screens/TechTree.ts` (a pause card like `SaveSlots`) plus a pure `techTreeModel(civ, age)` in `src/ui/screens/techTreeModel.ts`. The model is built from the existing balance and availability tables (`BUILDING_SPECS`, unit specs and trainers, `technologies.ts`, the age-up cost), never duplicated. It has three columns, one per age, and each column lists the age's new buildings, its units with the building that trains each, its techs, and the cost of entering the age. The current age is highlighted and later ages are dimmed. The pause menu gets "Fejlődési fa" between "Betöltés" and "Beállítások". The `techTree` key opens the pause on this card.
8. **Scores.** `src/stats/MatchStats.ts` keeps, per player:
   - `gathered` (sum of all resources delivered);
   - `killValue` (cost sum of enemy units and buildings this player destroyed, from the killer in `CombatSystem` / `TowerCombatSystem` / projectiles via a `gameEvents` kill event, which already exists or is added);
   - `unitsTrained`, `unitsLost`, `buildingsBuilt`, `buildingsLost`, and `ageUpAtMs[]`.

   `score(player, stats, world) = floor(gathered/10) + floor(killValue/10) + floor(standingBuildingValue/10) + AGE_SCORE[age]`, with `AGE_SCORE = {1: 0, 2: 300, 3: 800}`. These constants go in `config/balance.ts` as `SCORE_BALANCE`. `standingBuildingValue` is the cost sum of the player's completed, living buildings.

   `MatchStats` is serialised into the save: `schemaVersion` becomes 2, and `src/save/migrations/` gets `v1→v2`, which adds zeroed stats. The migration is tested per §11.1. A timeline sample (`{ tMs, scores[], pops[] }`) is taken every 60 game seconds and kept in `MatchStats`, so it is saved too.
9. **Right panel.** `src/ui/panels/SidePanel.ts` is a collapsible glass panel on the right edge, vertically between the clock and the build panel. It has two views, "Pontszám" and "Falusiak", with tabs in its head. The `scorePanel` key toggles it open and closed. The `villagerPanel` key, or a click on the top bar's population counter, opens it on the Falusiak view. Its open state and view live in `uiStore` and are not saved.
   - **Pontszám:** a row per player, sorted by score: the colour dot, the civ name (the human's row is marked "Te"), the score, and a thin bar relative to the leader. Defeated players are struck through.
   - **Falusiak:** rows for Étel / Fa / Arany / Építés / Tétlen / Egyéb (for example moving with no task), each with a count. The Tétlen row is highlighted when it is above 0.
   - A click on a Falusiak row selects exactly those villagers, using `SelectionSystem`'s multi-select, and plays the select sound.
   - The data comes through `HudSync` each tick, in the throttled way the HUD already uses, and goes into `uiStore`. The counting is a pure function `villagerActivity(world, playerId)` in `src/stats/villagerActivity.ts`.
10. **Camera buttons.**
    - "Haza" (a house icon) sits in the top-left brand row. It and the `home` key centre the camera on the human's living, completed town centres in id order, and each press moves to the next one.
    - The minimap card gets "+" and "−" buttons. Each press zooms one wheel notch around the screen centre, within `MIN_ZOOM` and `MAX_ZOOM`.
    - Both call methods on `CameraController` (`centerOnTile(tile)` and `zoomStep(dir)`).
11. **Match log.** `src/stats/matchLog.ts` uses a separate localforage instance, `name: 'isorts', storeName: 'matches'`, key `match:<createdAt ISO>`, with a zod schema. The record is written once per match:
    - when the game-over screen appears;
    - on "Kilépés a főmenübe" from the pause, with `outcome: 'abandoned'`;
    - never for a match that was loaded and then left without any play (game time unchanged).

    The record contains the setup config, the civs, AI difficulty and personalities, the map, the seed, the victory mode, the duration, the outcome, each player's final stats and score breakdown, and the timeline. The log keeps at most 200 records and drops the oldest.

    The main menu gets "Statisztika" with a screen showing:
    - the totals: matches, win rate, average length, best score;
    - breakdowns by the human's civ and by difficulty;
    - a list of the most recent 50 matches, newest first;
    - an "Exportálás (JSON)" button that downloads all records as one file through an object-URL `<a download>`.

    A corrupt record is skipped and counted.
12. **Music.** The existing generative system gets more dynamic, with no new architecture. The changes:
    - A percussion layer: a synthesised frame drum or low tom pattern per age, quiet in calm mood and stronger in battle.
    - An intensity parameter in `MusicDirector`, 0..1, smoothed. It comes from the battle detector, the number of the human's units in motion, and the age.
    - Intensity scales the note density, adds an ostinato voice above 0.5, and raises the tempo by up to +12 % between phrases, never mid-phrase.
    - Phrase variation: rhythmic displacement and octave leaps from the seeded RNG.

    Budgets: the bus level stays where Task 9 of M6 set it, and the voice cap stays 16. The WAV renders are redone into `shots/task-9/` for audition.
13. **i18n:** every new string is in `src/i18n/hu.ts`.
14. **Dev server for browser checks:** `npm run dev -- --port 5196 --strictPort` (the user's own server holds 5173 — never stop it).

## Review Focus

1. A villager ordered to build while it stands on a tile of the new foundation itself: it must step out and build, not freeze.
2. A quick succession of foundations placed across a moving group's path: no unit may end up inside.
3. A trackpad pinch must not also trigger the browser's page zoom, and a mouse wheel on Windows (`deltaMode` 0, ±100 steps) must still zoom in `auto` mode.
4. A load of an M6 (v1) save must still work after the v2 migration, with zeroed stats and no crash in the side panel.
5. Deleting a site that is being built, while builders are working on it, must release the builders and refund exactly once.
